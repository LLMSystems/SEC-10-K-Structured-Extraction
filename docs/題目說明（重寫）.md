# 面試題目：SEC 10-K 財報 Item-level 結構化抽取 Pipeline

## 測驗目的

這份題目不是在考你能不能寫出能跑的程式碼——AI 工具讓這件事已經相對容易做到。我們真正想評估的是：

> **當你面對模糊、混亂、需要大量判斷的真實問題時，你如何與 AI 協作，並把一次性的原型轉變成一個可靠、可維護的系統？**

我們具體在意以下幾個面向：

| 評估項目 | 具體含意 |
|---|---|
| **評估紀律** | 你如何設計測試來確認系統「真的對」？ |
| **系統性思考** | 面對真實資料的雜亂與失敗，你如何分解問題？ |
| **工程權衡** | 你對成本、延遲、可靠性如何取捨與決策？ |
| **AI 協作品質** | 你跟 AI 工具的互動方式能不能真正放大你的產出？ |

---

## 題目說明

### 背景

美國上市公司每年須向 SEC（美國證券交易委員會）提交 **Form 10-K 年報**。10-K 有官方規範的結構，分為 Part I～IV，底下共有 Item 1～16。但現實中，不同公司、不同年份的格式差異極大：

- HTML 格式與標籤用法不統一
- 標題寫法多元（大小寫、空格、特殊字符等皆有）
- 舊格式為純文字或 SGML，無 HTML 結構
- Part III 常以「incorporated by reference」形式，指向另一份 Proxy Statement（委託書），不含實際內容
- 部分 Item 標記為「Not Applicable」或「Reserved」，無實質內容

### 你的任務

建立一個 **結構化抽取 Pipeline**，輸入一份 10-K，輸出標準化的 JSON。

---

## 輸入規格

接受以下兩種輸入方式（擇一）：

```
CIK（公司識別碼）+ Accession Number（申報編號）
```
或

```
10-K 檔案的直接 URL
```

---

## 輸出規格

輸出為 JSON 格式，結構如下：

```json
{
  "filing_info": {
    "cik": "0000320193",
    "accession_number": "0000320193-23-000106",
    "company_name": "Apple Inc.",
    "fiscal_year_end": "2023-09-30"
  },
  "items": [
    {
      "part": "Part I",
      "item_number": "1",
      "item_title": "Business",
      "content_text": "Apple Inc. designs, manufactures and markets...",
      "char_range": [1024, 45231],
      "status": "extracted"
    },
    {
      "part": "Part III",
      "item_number": "10",
      "item_title": "Directors, Executive Officers and Corporate Governance",
      "content_text": null,
      "char_range": null,
      "status": "incorporated_by_reference"
    }
  ]
}
```

### `status` 欄位說明

| 狀態值 | 意義 |
|---|---|
| `extracted` | 成功抽取到內容文字 |
| `incorporated_by_reference` | 此 Item 以「引用」形式指向另一份文件（常見於 Part III 指向 Proxy Statement） |
| `not_applicable` | 此 Item 對該公司不適用 |
| `reserved` | 此 Item 為 SEC 保留項目，無內容 |

## 部署要求

將你的 Pipeline 部署為一個 **REST API**，並部署到 **[Zeabur](https://zeabur.com)** 平台。

我們會用自己挑選的 10-K filings 呼叫你的 API 來驗證輸出。

---

## 資料來源：SEC EDGAR 官方 API（免費，無需 API Key）

| 用途 | URL |
|---|---|
| API 總覽 | `https://www.sec.gov/search-filings/edgar-application-programming-interfaces` |
| 公司申報歷史 | `https://data.sec.gov/submissions/CIK{10位補零}.json` |
| 全文搜尋 | `https://efts.sec.gov/LATEST/search-index?q={query}&forms=10-K` |
| 檔案下載 | `https://www.sec.gov/Archives/edgar/data/{CIK}/{accession-去破折號}/{filename}` |
| XBRL 財報數字（可用於交叉驗證） | `https://data.sec.gov/api/xbrl/companyfacts/CIK{10位補零}.json` |

> ⚠️ **API 使用規範**：每個 Request 必須帶 `User-Agent` header（格式：`公司名 聯絡Email`），速率限制為 10 req/sec，無需 API Key。

## Evaluation Set 要求

你需要**自行建立一個 evaluation set**，用來驗證你系統的準確性。

### 涵蓋範圍建議

- **不同產業**：科技、金融、製造、零售等
- **不同公司規模**：大型、中型、小型公司
- **不同年份**：新格式（近 5 年）與舊格式（2000 年以前）
- **刻意挑選 edge case**，包含：
  - Part III 為 incorporated by reference 的案例
  - 有 Not Applicable / Reserved 的案例
  - 純文字或 SGML 格式的舊申報
  - 非標準標題寫法（如全大寫、加底線、特殊字符分隔等）

### 驗證方式

在沒有公開 ground truth 的情況下，你需要說明你**如何驗證自己的系統是正確的**，例如：
- 人工抽樣標記部分結果作為 ground truth
- 交叉比對 XBRL 數據
- 使用多種解析策略互相對照

---

## 報告內容

除了程式碼與 API 之外，請一併提供：

1. **準確度報告**：每種 status 類型的準確率，整體 F1 或 exact-match 數字
2. **失敗模式分析**：哪些情況最容易出錯？原因是什麼？
3. **成本與延遲**：每次 API 呼叫的平均成本（如有使用 LLM）、P50/P95 延遲
4. **解析策略說明**：你選擇規則式 / LLM / 混合策略的理由與取捨

---

## 我們會重點評估的事

- Eval set 是否**刻意挑選 edge case**，而非只用簡單好解析的案例
- **解析策略的權衡**：規則式 vs. LLM vs. 混合——你的選擇是否有清楚的理由？
- **在沒有公開 ground truth 的情況下**，你如何自我驗證？
- `incorporated_by_reference` 是否被**正確偵測與標記**（不當成空白或錯誤處理）
- **成本紀律**：你是否有意識地控制 LLM 呼叫次數與費用？
